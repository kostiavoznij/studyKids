# Акаунти (Supabase)

Записи зберігаються в базі Supabase, вхід — через Google. Доступ мають лише пошти зі списку
`members` на сервері (адміністратори й менеджери) і пошти з карток вчительок; будь-хто інший після входу
бачить «немає доступу» і не отримує жодного запису.

| Проєкт | Ref | Для чого |
|---|---|---|
| `uroky` | `cecjmzwrrcerltreifsu` | опублікований застосунок (`app/.env.production`) |
| `uroky-test` | `vydjijtbqaqapmotenop` | розробка на `localhost:5199` (`app/.env.development`) |

Ключі `sb_publishable_…` у `.env.*` публічні за задумом. Секретний `service_role` ключ нікуди в код не кладемо.

## Як це влаштовано

- Кожен запис застосунку (учень, урок, оплата, податок…) — рядок у таблиці `records`: тип, id і весь запис у JSON.
- Пристрій відправляє змінені записи через `push_records()` — сервер лишає новішу зміну кожного запису —
  і забирає все, що новіше за останню бачену ревізію. Без інтернету застосунок працює як раніше й досилає зміни пізніше.
- Хто що бачить, перевіряє сама база (row level security і функції), а не інтерфейс — див. «Ролі».

Схема — у `supabase/migrations`.

## Ролі

| | Адміністратор | Менеджер | Вчителька |
|---|---|---|---|
| Розклад | усіх вчительок | усіх вчительок | лише свій |
| Учні, групи, ціни, оплати сімей | так | так | лише свої учні: клас, контакти, нотатки, теми — без цін і оплат |
| Створити / перенести / скасувати урок | так | так | ні |
| Відмітити «проведено», тема, домашка, засвоєння, нотатка | так | так | у своїх уроках |
| Вчительки (картки, Gmail) | так | так | ні |
| Фінанси, податки, звірка з банком, заробіток | так | ні | ні |
| Статистика | повна | без грошей | ні |
| Видалити учня чи групу назавжди | так | ні (лише архів) | ні |
| Налаштування → Доступ | так | ні | ні |

- `admin` і `manager` — рядки в `members` (Налаштування → Доступ).
- Вчителька входить через **картку вчительки** (Учні → Вчительки): запис типу `teachers` з її Gmail.
  Хто веде вчительок, той і керує їхнім входом. Картка в архіві — входу немає.
- Учні, групи, уроки й дні без уроків мають `teacherId`; без нього — вчителька `main`
  (та, що вела записи до появи кількох вчительок). Її картку створює міграція; ім'я змінюють у застосунку.
- Менеджер читає таблицю `records` без `taxes`, `taxPlans`, `bankMonths` і пише через `push_records()`
  лише дозволені типи; видалити живого учня чи групу сервер йому не дасть.
- Вчителька не читає `records` взагалі. `teacher_pull()` дає їй лише її уроки, учнів і групи з них,
  її картку й її дні без уроків — з ціною 0 і без розкладу; `gone` каже, які уроки передано іншій.
  `teacher_push()` бере з її змін лише «проведено / заплановано», тему, домашку, нотатку, звіт пробного уроку
  й оцінки та відсутність учасників; час, ціну, вчительку й скасування не чіпає.
- Коли роль пристрою змінюється, він починає з порожньої копії й забирає те, що дозволено новій ролі.
- Дні без уроків — окремо для кожної вчительки або «для всіх» (`teacherId: '*'`).
- **«Учень не прийшов».** Вчителька не скасовує уроки, а позначає неявку (`missed` на уроці; `teacher_push()`
  приймає її лише на запланованому уроці). Урок лишається запланованим, у календарі адміністратора й менеджера
  з'являється банер «потрібне ваше рішення»: скасувати (оплачується чи ні) або прибрати позначку.
- **Оплата вчительок** — лише адміністратор. Ставка (`teacherPay`, id = id вчительки: за урок, за годину або
  відсоток від ціни; окремо — чи платити за пробні й за пізні скасування) і виплати (`teacherPayouts`).
  Менеджер їх не читає й не пише (їх немає в `manager_types()`), до вчительки вони не потрапляють.
  Нараховане рахується за проведеними уроками; «до виплати» = нараховане за весь час − виплати.
- **Статистика вчительок:** Статистика → «По вчительках». Зароблене — за вчителькою, яка провела урок;
  оплата сім'ї — за вчителькою групи (групова оплата) або за теперішньою вчителькою учня.

## Додати людину

- **Вчителька:** Учні → Вчительки → «+ Вчителька» (адміністратор або менеджер), вказати її Gmail.
- **Адміністратор чи менеджер:** Налаштування → Доступ → «Додати пошту» (лише адміністратор). Там же
  змінюють роль та ім'я або забирають доступ. Список живе в таблиці `members`; змінювати його можна
  лише через функції `set_member()` / `remove_member()`, які перевіряють, що це робить адміністратор.
  Адміністратор не може забрати доступ у себе чи зняти з себе права — це робить інший адміністратор,
  тож застосунок не лишиться без жодного.

Вхід через Google опубліковано (In production), тож Google пускає будь-яку пошту, а доступ вирішує лише сервер.

Якщо доступ загублено (наприклад, видалено всіх адміністраторів напряму в базі), повернути його можна командою:

```bash
npx supabase db query --remote=cecjmzwrrcerltreifsu --yes \
  "insert into public.members (email, role, name) values ('пошта@gmail.com', 'admin', 'Ім''я')
   on conflict (email) do update set role = 'admin'"
```

## Змінити базу

Новий SQL-файл у `supabase/migrations`, потім спершу тест, після перевірки — робочий:

```bash
npx supabase db push --remote=vydjijtbqaqapmotenop --yes
npx supabase db push --remote=cecjmzwrrcerltreifsu --yes
```

## Перенести пристрій в акаунт

Ще → Акаунт → «Увійти через Google». Пристрій з демо-даними або порожній просто отримує записи акаунта.
Якщо на пристрої є свої записи, застосунок питає: «Перенести в акаунт» (додати їх, новіша зміна перемагає)
чи «Не переносити» (прибрати їх і взяти лише записи акаунта). Google Таблиця після переходу відключається
й лишається архівом.
